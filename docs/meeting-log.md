# 設計ディスカッションログ

## 2026-01-10 — 初期設計ミーティング

### 議題: プロジェクトの方向性と技術スタックの確定

**背景:**
読書メーターと Filmarks の個人データを手元で管理したい。両サービスとも公式 API がなく、ブラウザからしかアクセスできない。自分のデータなのに自由に取り出せないのは不便であるという問題意識から議論をスタートした。

**決定事項:**

- **ランタイムは Bun に統一する。** Node.js でも動作するが、`bun:sqlite` が内蔵されており追加依存なしで SQLite を扱える点と、TypeScript のネイティブ実行で開発サイクルを短縮できる点を重視した。
- **フレームワークは Hono を採用する。** Express はやや古く、型サポートが弱い。Fastify は高機能すぎる。Hono はシンプルかつ TypeScript ファーストで、将来的に Cloudflare Workers へ移行する可能性も残せる。
- **スクレイピングは Cheerio で十分。** 対象サービスは JavaScript なしでも HTML が返ってくると仮定し（要確認）、ヘッドレスブラウザは使わない方針とした。必要になった場合は Playwright を後付けで組み込む。

## 2026-01-14 — スクレイパーアーキテクチャの設計

### 議題: プラグイン構造の設計

**論点:**
スクレイパーを増やしていくにあたり、どう構造化するか。

**選択肢の比較:**

| 案 | 内容 | 評価 |
|---|---|---|
| A | switch 文で分岐 | 拡張のたびに中央ファイルを変更が必要。NG |
| B | クラスベースの継承 | TypeScript では interface + object literal の方がシンプル |
| C | ScraperPlugin interface + registry | 追加がモジュール単体で完結する。採用 |

**決定事項:**

- `ScraperPlugin` インターフェースを定義し、各スクレイパーはこれを実装したオブジェクトとして export する。
- `sync` メソッドは `AsyncGenerator<ScrapeRecord>` を返す。ストリーミング処理でメモリ効率が良く、将来的に大量データにも対応しやすい。
- レジストリパターンを採用し、`initRegistry()` を起動時に一度呼ぶだけで全スクレイパーが登録される。

## 2026-01-17 — DB スキーマの確定

### 議題: books / movies の正規化とクレデンシャルの扱い

**クレデンシャルの扱いについて:**

環境変数での管理（`.env` ファイル）と DB 内での管理を比較した。

- 環境変数: コンテナ再起動なしに変更できない。複数スクレイパーの設定を UI から変更できない。
- DB 内 JSON: 管理ダッシュボードから更新可能。ただし DB の保護が必要。

今回はシングルユーザー・ローカル運用を前提として DB 内 JSON を採用した。本番公開する場合は暗号化または環境変数へのフォールバックを検討する。

**raw_json カラムについて:**

将来のスキーマ変更に備え、スクレイピングで取得した全データを JSON で保存する。正規化済みカラムが足りなくなった場合の再処理コストを抑えるための保険。

## 2026-01-21 — 管理ダッシュボードの設計

### 議題: フロントエンドの技術選定

**基本方針:**
内部ツールなので見た目よりも機能性と保守性を重視する。ビルドパイプラインを持ちたくない。

**選定:**
- Tailwind CDN: クラスだけでデザインが完結。`tailwind.config` でカスタムカラー定義も可能。
- Alpine.js CDN: `x-data` / `x-init` で SPA ライクな挙動を単一ファイルで実現できる。React/Vue のビルドは不要。
- 単一 HTML ファイル: `src/admin/index.html` として Hono で配信。デプロイが単純。

**デザイン方針:**
- ダークテーマ（グレー系）: 開発ツールの文脈に馴染む。長時間の使用に目への負担が少ない。
- ステータスバッジの色分け: completed=緑、failed=赤、running=青、pending=グレー。
- サイドバー固定 + メインコンテンツスクロール: 標準的な管理画面 UX。

## 2026-01-24 — コンテナ化とデプロイ戦略

### 議題: Docker 構成の設計

**決定事項:**

- マルチステージビルド: `deps` ステージで `bun install`、`runner` ステージで実行。イメージサイズを削減。
- データボリューム: `./data:/app/data` のバインドマウントで SQLite ファイルをホストに永続化。コンテナ削除でもデータが失われない。
- `restart: unless-stopped`: 予期せぬクラッシュからの自動復旧。
- ヘルスチェック: `/health` エンドポイントを 30 秒ごとに確認。Docker が自動的に異常を検知できる。

**今後の課題:**

- データのバックアップ戦略: SQLite ファイルを定期的に S3 等にアップロードする仕組みが必要。
- 認証: 現状はネットワーク境界（VPN、ローカル LAN）に依存。必要に応じて Bearer トークン認証を追加する。
- スクレイパーの実装: 現在はスタブ。実際の HTML 構造を確認しながら Cheerio パーサーを実装する必要がある。セッション Cookie の取得方法についても調査が必要。
