## 決定事項

### 1. バックエンドを FastAPI (Python) に切り替える

**決定**: Bun/Hono/TypeScript から FastAPI/Python/SQLAlchemy に移行する。

**理由**:
- FastAPI の自動 OpenAPI 生成により、インターフェースドキュメントがコードから自動で得られる
- Pydantic v2 によるバリデーションが強力で、外部入力（スクレイパーからのペイロード）のガード役として信頼できる
- Python + SQLAlchemy のエコシステムは本件のようなデータ受信・保存サービスに成熟している
- 将来の ML/データ分析との連携を考慮すると Python スタックの方が合流しやすい

### 2. フロントエンドを React + Vite に切り替える

**決定**: Alpine.js の単一 HTML ファイルから React + Vite SPA に移行する。

**理由**:
- ダッシュボードの複雑度が増すにつれ、コンポーネント分割と状態管理が必要になる
- TypeScript で型付きの API クライアントを書ける
- Vite の HMR により開発体験が大幅に向上する

### 3. スクレイピングロジックは完全に外部（OpenClaw）に移管する

**決定**: arigato-gateway 自体はスクレイピングを行わない。正規化済みペイロードを受け取るだけのインジェスタに徹する。

**理由**:
- スクレイピングはセッション管理・Cloudflare 対策等で変更頻度が高い
- ゲートウェイ側の責務を「受信・保存・閲覧」に限定することで保守性が上がる
- OpenClaw Browser Relay が実際のブラウザセッションを持つため、より高い成功率が見込める

### 4. データモデルの統一

**決定**: `sources / runs / records / ingest_errors` の 4 テーブル構成を採用する。

- `sources`: ソース（bookmeter, filmarks 等）のレジストリ
- `runs`: 同期セッションの開始・終了・件数を管理
- `records`: 実際のデータ（本・映画等）を正規化して保存
- `ingest_errors`: バリデーションに失敗したペイロードのログ

**理由**: books/movies を別テーブルにする案もあったが、将来ソースが増えるたびにテーブルを追加するのは管理コストが高い。`record_type` カラムで区別し、ソース固有フィールドは `payload: JSON` で保持する戦略を採用。

### 5. 認証は MVP では省略

**決定**: 内部 LAN 専用として認証なしで運用する。CORS で frontend origin のみ許可。

**将来**: Tailscale による境界防御、または Bearer トークン認証を追加予定。
